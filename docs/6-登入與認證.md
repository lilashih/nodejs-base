# 6. 登入與認證

本系統提供兩種登入方式：**Cookie Session** 與 **Bearer Token**，並基於同源架構設計雙軌認證、JWT 簽章與驗證規則、CSRF 防護與錯誤處理機制。

Cookie Session 是以 Cookie 攜帶 JWT，並非伺服器保存 Session ID 與狀態的 session store 架構。整體架構設計詳見 [第 0 篇：架構總覽](0-架構總覽.md)，同源安全性詳見 [第 2 篇：同源架構、CORS 與 CSRF 機制](2-同源架構、CORS與CSRF機制.md)，前端狀態管理見 [第 9 篇：前端開發](9-前端開發.md)。

---

## 一、雙軌登入方式概述與選擇

專案針對瀏覽器前端與第三方 API 客戶端提供兩種登入端點：

| 使用情境 | 登入端點 | 認證方式與標頭 | 登入回應 | CSRF 防護要求 |
| :--- | :--- | :--- | :--- | :--- |
| **本專案 Vue 前端或同源瀏覽器頁面** | `POST /api/auth/session/login` | 瀏覽器自動攜帶 `HttpOnly` Cookie (`token`) | `{ user }` | **受 `csrfMiddleware` 嚴格保護**<br>（檢查 Origin / Referer Host） |
| **CLI 命令列、行動 App 或第三方系統** | `POST /api/auth/login` | 客戶端自行附帶<br>`Authorization: Bearer <token>` | `{ user, token }` | **不受 CSRF 限制**<br>（非瀏覽器自動攜帶機制） |

---

## 二、JWT 簽發與資料流程

使用者登入驗證通過後，伺服器使用 HS256 演算法簽發 JWT，以使用者 ID 作為 `subject`（`sub`），並配置有效期限、發行者（`issuer`）與受眾（`audience`）。

### 2.1 安全守則與金鑰相容性

* **禁止存放敏感資料**：JWT 的簽章僅保護資料完整性，不提供 payload 加密，因此**嚴禁將密碼、金鑰或機密資訊放入 payload**。
* **變更金鑰影響**：變更 `.env` 中的 `JWT_SECRET` 會導致所有既有已簽發的 Token 立即失效；變更 `issuer` 或 `audience` 也會影響驗證相容性，部署前須妥善評估使用者重新登入之影響。

## 三、Cookie Session 登入機制

### 3.1 登入請求與安全設定

用戶端發送登入請求：

```http
POST /api/auth/session/login
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "yourPassword"
}
```

登入成功時回傳 HTTP 200，伺服器於回應標頭設定 `Set-Cookie`，回應 Body 僅包含使用者資訊，不會暴露 JWT：

```json
{
  "message": "登入成功",
  "data": {
    "user": {
      "id": 1,
      "name": "使用者",
      "email": "user@example.com",
      "createdAt": "2026-01-01 00:00:00",
      "updatedAt": "2026-01-01 00:00:00"
    }
  }
}
```

專案使用名稱為 `token` 的 Cookie 儲存 JWT，並套用以下安全屬性：
* **`HttpOnly`**：禁止前端 JavaScript 透過 `document.cookie` 讀取 Token，徹底杜絕 XSS 竊取。
* **`Path=/api`**：限制 Cookie 僅在發送 `/api` 請求時攜帶，縮小作用範圍。
* **`SameSite=Lax`**：限制跨站請求自動攜帶 Cookie，提升跨站請求防禦力。
* **`Secure`**：當 `COOKIE_SECURE=true`（正式環境推薦）時啟用，限制僅透過 HTTPS 加密連線傳送。
* **有效期限**：Cookie 保存期限依據 JWT 到期時間動態設定（預設 `JWT_EXPIRES_IN=1h`）。

### 3.2 查詢登入狀態（`GET /api/auth/me`）

呼叫 `GET /api/auth/me`，認證成功後回傳 `{ user }`，未登入、JWT 已過期或無效時回傳 HTTP 401。
前端每次重新整理頁面時，皆主動呼叫此 API 以還原畫面上的登入狀態，**不在 `localStorage` 存放 Token 或登入資訊**。

### 3.3 登出（`POST /api/auth/session/logout`）

呼叫 `POST /api/auth/session/logout`，伺服器會以相同名稱與 Path 覆蓋並清除 Cookie，回傳 HTTP 200。
即使 JWT 已過期仍可正常呼叫此端點完成登出；若網路請求異常中斷，Cookie 可能仍留存於瀏覽器，應提示重試。

## 四、Bearer Token 登入機制

適用於不受瀏覽器 Cookie 管理之外部整合、CLI 工具或行動端 App。

### 4.1 登入與授權標頭

發送 `POST /api/auth/login` 登入成功後，伺服器回傳 `{ user, token }`，後續存取受保護端點時，客戶端必須自行在 HTTP 請求標頭附帶：

```http
Authorization: Bearer <token>
```

### 4.2 生命週期與撤銷特性

由於 JWT 本質為無狀態（Stateless）簽章，本專案目前未配置 Redis 黑名單或 Refresh Token 撤銷機制：
* 呼叫 `POST /api/auth/session/logout` 僅清除瀏覽器 Cookie，**不會撤銷已簽出的 Bearer Token**。
* 已簽出的 Bearer Token 在到期時間（`exp`）到達前皆保持有效，若需即時失效須等待其自然過期或更換全域 `JWT_SECRET`。

## 五、認證中介層機制（`authMiddleware`）

全域認證中介層 [src/http/middleware/authMiddleware.js](../src/http/middleware/authMiddleware.js) 依以下確定順序判斷請求憑證：

1. **優先讀取 Cookie**：檢查請求標頭中名稱為 `token` 的 Cookie。
2. **退回檢查 Authorization**：若未攜帶 Cookie 或值為空字串，才讀取 `Authorization: Bearer <token>` 標頭。
3. **驗證與注入**：驗證選定之 JWT 簽章、期限、演算法（HS256）、issuer 與 audience；通過後將使用者 ID 放入 `req.user.id`，記錄認證來源 `req.authSource`（`cookie` 或 `bearer`），並透過 `setUserId()` 綁定至非同步日誌上下文。

> [!WARNING]
> **憑證互斥原則**：若請求中攜帶了 Cookie 但該 Cookie 已失效或過期，中介層將**直接拋出 HTTP 401 錯誤，絕不會退回嘗試同請求中的 Bearer 標頭**。若同時提供合法的 Cookie 與 Bearer Token，系統一律以 Cookie 的身分為準。

## 六、Cookie 寫入請求與 CSRF 防護機制

為確保 Cookie Session 模式下的操作安全，掛載 [src/http/middleware/csrfMiddleware.js](../src/http/middleware/csrfMiddleware.js) 的寫入路由在認證通過後會執行嚴格檢查：

### 6.1 防護規則與比對機制

* **防護對象**：僅對 `req.authSource === "cookie"` 且 HTTP Method 為 `POST`、`PUT`、`PATCH`、`DELETE` 的寫入請求生效；**Bearer Token 請求不受此檢查限制**。
* **Host 比對規則**：比對請求標頭 `Origin` 或 `Referer` 的 Host（包含主機名稱與 Port，不限 http/https），必須與當前 API 請求的 `Host` 完全相符；若兩者皆為空或皆不相符，立即拋出 HTTP 403 `無效的跨站請求`。

### 6.2 跨來源部署注意事項

* 跨來源的 Cookie 寫入請求即使通過 CORS 預檢，若來源 Host 與 API Host 不同，仍會遭 CSRF 檢查拒絕。
* 反向代理（如 Nginx）設定時應確保傳遞正確的 `Host` 與 `X-Forwarded-*` 標頭，保留使用者公開存取的網址 Host，避免合法寫入被誤判為跨站攻擊。

## 七、環境設定與常見錯誤處理

### 7.1 核心環境變數配置

| 環境變數 | 型態與預設值 | 說明 |
| :--- | :--- | :--- |
| `JWT_SECRET` | 字串（至少 32 字元） | JWT 簽章私鑰，長度不足時系統啟動將直接報錯阻斷。 |
| `JWT_EXPIRES_IN` | 時間字串（預設 `1h`） | JWT 有效期限；Cookie 保存壽命亦連動此數值。 |
| `JWT_ISSUER` | 字串 | JWT 簽發者識別名稱，驗證時須完全一致。 |
| `JWT_AUDIENCE` | 字串 | JWT 目標接收對象識別名稱，驗證時須完全一致。 |
| `COOKIE_SECURE` | 布林值（`true` / `false`） | 是否啟用 Cookie 的 `Secure` 標籤（正式環境 HTTPS 務必設為 `true`）。 |
| `CORS_ORIGINS` | 逗號分隔網址清單 | 允許存取之跨來源清單；跨來源攜帶 Cookie 時前端需設定 `credentials: "include"`。 |

### 7.2 常見 HTTP 錯誤狀態碼

| HTTP 狀態碼 | 錯誤原因 | 排查方向 |
| :--- | :--- | :--- |
| **401 Unauthorized** | 憑證無效、Token 已過期或未提供授權憑證。 | 檢查登入帳密、確認 Cookie 是否被瀏覽器清除或 Token 是否逾期。 |
| **403 Forbidden** | 跨站請求檢查失敗（CSRF），或存取非本人所有之資源。 | 確認請求標頭是否攜帶正確的 `Origin` / `Referer`，檢查 Nginx 反向代理之 `Host` 標頭設定。 |
| **422 Unprocessable** | 輸入欄位校驗不符合規範。 | 檢查登入之帳號或密碼格式是否符合 API 規格限制。 |
