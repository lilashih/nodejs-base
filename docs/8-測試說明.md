# 8. 測試說明

本篇說明專案之自動化測試架構、設計理念、測試範圍與執行指令，專案透過完整的單元測試、HTTP API 測試與前端型別檢查，確保系統各層模組在重構與迭代過程中的穩定性。

---

## 一、測試架構

### 1.1 測試工具棧

- **後端測試框架**：[Jest](https://jestjs.io/)，搭配 `module-alias` 支援 `@src/*` 絕對路徑別名（對應 `<rootDir>/src/*`）。
- **HTTP 介面測試**：[Supertest](https://github.com/ladjs/supertest)，直接對 Express 應用實例（`src/http/app.js`）發起請求，無需啟動真實 HTTP 伺服器監聽 Port，具備極高的執行速度。
- **前端型別與靜態檢查**：`vue-tsc`，負責 Vue 3 SFC 元件與 TypeScript/JavaScript 靜態型別檢驗。
- **全域語法檢查**：專案自訂 `scripts/checkSyntax.js`，檢驗全專案 JS 檔案語法與 camelCase 命名規範。

### 1.2 測試環境隔離（`.env.test` 與 `.env.test.local`）

測試程式透過 Node.js 原生參數載入機制，將測試設定與一般開發環境隔離，避免測試過程影響正式資料：

| 檔案 | 用途 | 版本控制 |
| :--- | :--- | :--- |
| `.env.test` | 所有開發者共用的測試預設值，必要的設定檔，包含資料庫、Port 及前端路徑。 | 納入 Git。 |
| `.env.test.local` | 選用設定檔，用於覆寫個人環境的資料庫帳號、密碼及連線設定。 | 由 `.gitignore` 排除。 |

測試指令使用 `node --env-file=.env.test --env-file-if-exists=.env.test.local`，依序載入兩個檔案。同名設定以 `.env.test.local` 為準，未覆寫的設定沿用 `.env.test`。

pnpm test、pnpm test:unit 與 pnpm test:coverage 均使用此機制。

隔離原則：
- **資料與驗證隔離**：使用獨立的測試資料庫及 `JWT_SECRET` ，**嚴禁指向正式或共用資料庫**。
- **前端資源隔離**：透過 `APP_FRONTEND_PATH` 指向測試專屬的模擬靜態資源，無須預先建置正式前端即可執行 API 測試。

### 1.3 Mock 隔絕策略

- **單元測試（Unit Test）**：核心業務邏輯（Service）測試時，使用 Mock 隔絕外部系統（如資料庫連線、磁碟檔案系統），專注驗證計算邏輯、例外分支與轉換結果。
- **API 測試（API Test）**：通常以 `jest.mock()` 模擬底層 Service 回應，專注驗證 HTTP 標頭、輸入欄位驗證器（express-validator）、中介軟體（Middleware）、狀態碼以及統一回應結構。

## 二、測試範圍與分類

專案測試檔案集中於 `test/` 目錄，主要劃分為單元測試與 API 測試：

| 類別 | 目錄位置 | 涵蓋重點與驗證模組 |
| :--- | :--- | :--- |
| **單元測試** | `test/unit/` | 業務邏輯、Helper 工具、資料庫連線池、日誌與自訂例外。 |
| **HTTP 契約測試** | `test/api/` | Supertest 驗證路由、欄位驗證、認證流程、權限、CORS 與靜態路由 Fallback。 |
| **前端檢查** | `frontend/` | `vue-tsc --noEmit` 驗證 Vue SFC 元件與前端 JavaScript 型別。 |
| **全域語法** | `scripts/` | `checkSyntax.js` 驗證後端、測試與腳本之 JS 語法與 camelCase 命名。 |


## 三、測試指令與執行指南

所有測試與檢查指令均於專案根目錄執行。

### 3.1 常用測試指令

| 指令 | 操作目標 | 說明 |
| :--- | :--- | :--- |
| `pnpm test` | 完整測試 | 執行所有 Jest 單元測試與 API 測試。 |
| `pnpm test:unit` | 單元測試 | 執行 test/unit/ 下的測試，無須啟動資料庫。 |
| `pnpm test:coverage` | 覆蓋率分析 | 執行測試並產生程式碼覆蓋率報告。 |
| `pnpm --dir frontend check` | 前端型別檢查 | 使用 vue-tsc --noEmit 檢查 Vue 與 TypeScript 型別。 |
| `pnpm check` | 後端語法檢查 | 透過 `node scripts/checkSyntax.js` 檢查 JavaScript 語法與命名規範。 |

### 3.2 進階測試指令

指定單一測試檔案：

```bash
node --env-file=.env.test --env-file-if-exists=.env.test.local ./node_modules/jest/bin/jest.js --runInBand test/unit/requestHelper.test.js
```

依測試案例名稱篩選：

```bash
node --env-file=.env.test ./node_modules/jest/bin/jest.js --runInBand -t "健康檢查"
```

其中，`--runInBand` 表示依序執行測試，`-t` 則用於篩選名稱符合條件的測試案例。

## 四、編寫新測試的規範與最佳實踐

為確保測試程式的一致性、可維護性與可靠性，新增或修改測試時應遵循以下規範：

### 4.1 命名與語言規範
- **檔案命名**：使用 `camelCase`，並以 `.test.js` 結尾，例如 `userProfile.test.js`。
- **目錄分類**：單元測試放置於 `test/unit/`，API 測試放置於 `test/api/`。
- **測試描述**：`describe` 與 `test` 一律使用**繁體中文**，明確描述測試情境及預期結果。

### 4.2 統一路徑別名
測試檔案頂部應註冊模組別名，並統一使用 `@src/*` 引入後端模組，避免使用長路徑（如 `../../src/`）：
```javascript
require("module-alias/register");

const app = require("@src/http/app.js");
const { request } = require("@src/helper/request.js");
```

### 4.3 API 回應格式驗證
API 測試須驗證統一的 JSON 回應結構，確保包含 `message`、`data` 欄位及` X-Request-Id` 追蹤標頭：
```javascript
const response = await request(app).get("/api/health").expect(200);

expect(response.body).toHaveProperty("message");
expect(response.body).toHaveProperty("data");
expect(response.headers["x-request-id"]).toBeTruthy();
```

### 4.4 Mock 清理與測試隔離
- Mock 清理：Jest 已設定 clearMocks: true，各測試案例結束後會自動清除 mock 呼叫紀錄；若修改 Mock 實作或模組狀態，仍須視情況自行還原。
- 測試確定性：測試結果應可重現，避免依賴執行順序、外部服務或不穩定的環境狀態。
- 避免副作用：測試不得影響正式資料或外部環境，產生的暫存檔案及測試資料應於結束後清理。

## 五、程式修改後的測試驗收流程

每次修改或擴充功能後，建議依序執行以下檢驗：

1. **後端模組變更**：
   - 執行受影響的單元測試（例如 `pnpm test:unit`）。
   - 執行全專案語法與命名檢查（`pnpm check`）。
2. **API 路由或契約變更**：
   - 同步更新 `src/swagger/openapi.yaml`。
   - 執行對應的 API 測試（例如 `test/api/`）。
3. **前端程式碼變更**：
   - 執行前端型別檢查（`pnpm --dir frontend check`）。
   - 執行前端建置驗證（`pnpm build:frontend`）。
